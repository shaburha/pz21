# Разъяснение к работе

Этот файл объясняет, как устроен проект, почему он устроен именно так, и что показывать/говорить при защите.

## 1. Идея в двух словах

Раньше (ЛР №1–3) сервер отдавал **JSON**, а страницу рисовал клиент (React в ЛР №4). Здесь сервер сам собирает **готовый HTML**: берёт шаблон `.ejs`, подставляет в него данные из массива и отправляет браузеру. Это называется серверный рендеринг (SSR).

Каждый запрос проходит через **конвейер middleware** — цепочку функций `(req, res, next)`. Каждая функция что-то делает и либо передаёт запрос дальше (`next()`), либо сама отвечает.

## 2. Путь одного запроса

Пример: пользователь открывает `GET /item/1?auth=1`.

```
Браузер
  │  GET /item/1?auth=1
  ▼
logger            → печатает "[время] GET /item/1?auth=1", подписывается на окончание ответа
  ▼ next()
express.static    → ищет файл public/item/1 — нет такого → next()
  ▼
express.urlencoded→ тело пустое (GET) → next()
  ▼
identifyUser      → auth=1 → req.user = Иван Иванов, res.locals.authQuery = '?auth=1'
  ▼ next()
router: GET /item/:id → controller.show
  │   находит документ id=1 → res.render('item', { document, ... })
  ▼
EJS: item.ejs + partials/header + partials/footer → HTML → браузер (200)
  ▼
logger ('finish') → печатает "GET /item/1?auth=1 -> 200 (7 мс)"
```

Если документа нет (`/item/99`), контроллер вызывает `next()` без ответа → запрос проходит мимо остальных маршрутов → попадает в `notFound` → рендерится `404.ejs`.

Если в обработчике выброшено исключение (`/error`), Express пропускает все обычные middleware и сразу вызывает обработчик с **четырьмя** параметрами — `serverError` → `500.ejs` + стек в консоль.

## 3. Файлы и их роль

| Файл | Зачем |
| --- | --- |
| `server.js` | «сборка» приложения: настройка EJS (`view engine`, `views`), helper `formatDate` в `app.locals`, **порядок** middleware, монтирование маршрутов, обработчики ошибок в конце |
| `data/documents.js` | «база данных» — обычный массив в памяти и функции `getAll`, `getById`, `create`. При перезапуске сервера добавленные документы пропадают — это ожидаемо по заданию |
| `controllers/documentsController.js` | логика страниц: какие данные достать и какой шаблон отрендерить. Здесь же валидация формы |
| `routes/documents.js` | связывает URL с контроллерами; на `/add` стоит `requireAuth` — пример middleware только для конкретного маршрута |
| `middleware/logger.js` | логирование: время, метод, URL; после ответа — статус и длительность (событие `res.on('finish')`) |
| `middleware/auth.js` | имитация авторизации (см. раздел 4) |
| `middleware/errorHandlers.js` | `notFound` (404) и `serverError` (500) |
| `views/partials/*` | общие куски: шапка с `<html><head>`, подвал, бейдж статуса. Это и есть «layout» через partials |
| `views/*.ejs` | страницы: список, детальная, форма, вход, 404, 500 |
| `public/css/style.css` | статика, отдаётся `express.static` по адресу `/css/style.css` |

## 4. Как работает имитация авторизации

Задание: «проверяет наличие `?auth=1`. Если нет — редирект на `/login` (или `req.user = { name: 'Гость' }`)». В проекте сделаны **оба варианта**, каждый там, где он уместен:

1. `identifyUser` — подключён глобально, для всех запросов. Смотрит `req.query.auth`:
   - `'1'` → `req.user = { name: 'Иван Иванов', email: ..., isGuest: false }`;
   - иначе → `req.user = { name: 'Гость', isGuest: true }`.

   Также кладёт `user` и `authQuery` в `res.locals` — поэтому шапка в любом шаблоне знает, кого показывать, а все ссылки дописывают `?auth=1`, и авторизация не теряется при переходах.
2. `requireAuth` — подключён только к `GET /add` и `POST /add`. Гостя перенаправляет на `/login?returnTo=/add`. Страница входа — кнопка, ведущая на `/add?auth=1`.

Итог: смотреть документы может любой, создавать — только «вошедший». Настоящей безопасности тут нет (любой может дописать `?auth=1`) — это учебная заглушка; в реальном проекте использовались бы сессии или JWT (как в ЛР №3).

## 5. Почему middleware стоят именно в таком порядке

```js
app.use(logger);              // 1 — первым, чтобы видеть ВСЕ запросы и мерить полное время
app.use(express.static(...)); // 2 — CSS отдаётся сразу, без авторизации и парсинга тела
app.use(express.urlencoded);  // 3 — до маршрутов, иначе в POST /add req.body будет undefined
app.use(identifyUser);        // 4 — до маршрутов, им нужен req.user
app.use('/', documentsRouter);// 5 — маршруты
app.use(notFound);            // 6 — сюда доходит только то, что никто не обработал
app.use(serverError);         // 7 — последним: ловит ошибки из всего, что выше
```

Если поменять местами, например, `notFound` и роутер — любая страница будет 404. Если `serverError` поставить до маршрутов — он никогда не получит их ошибки.

## 6. EJS: что нужно знать

| Тег | Что делает | Пример из проекта |
| --- | --- | --- |
| `<%= x %>` | выводит значение **с экранированием** HTML (защита от XSS) | `<%= document.title %>` |
| `<%- x %>` | выводит **без экранирования** — только для доверенного HTML | `<%- include('partials/header') %>` |
| `<% код %>` | выполняет JS без вывода: циклы, условия | `<% documents.forEach((doc) => { %>` |

Откуда шаблон берёт переменные:
- из `res.render('index', { documents, ... })` — данные конкретной страницы;
- из `res.locals` — данные запроса (`user`, `authQuery` из `identifyUser`);
- из `app.locals` — общие для всего приложения (`appName`, helper `formatDate`).

Partials видят все эти переменные автоматически; локальные переменные цикла передаются явно: `include('partials/status-badge', { status: doc.status })`.

## 7. Форма добавления

1. `GET /add` → `add.ejs` с пустыми значениями.
2. Браузер отправляет форму `POST /add?auth=1` с телом `title=...&content=...&status=...&collaborators=...`.
3. `express.urlencoded` превращает тело в `req.body`.
4. Контроллер `create` проверяет: название ≥ 3 символов и уникально, статус из списка, участники — email через запятую.
5. Ошибки → та же форма с кодом **400**, списком ошибок и уже введёнными значениями (пользователю не нужно вводить всё заново).
6. Успех → `Documents.create(...)` (владелец — `req.user.email`) → **редирект** на `/?auth=1`.

Редирект после POST (паттерн Post/Redirect/Get) нужен, чтобы обновление страницы (F5) не отправило форму повторно и не создало дубликат.

## 8. Как проверить всё самому

```bash
npm install
npm start
```

| Действие | Ожидаемый результат |
| --- | --- |
| http://localhost:3000/ | список, в шапке «Гость», жёлтая подсказка |
| http://localhost:3000/?auth=1 | список, в шапке «Иван Иванов» |
| клик по документу | детальная страница `/item/1?auth=1` |
| http://localhost:3000/add (без auth) | редирект на `/login` |
| «Войти» → заполнить форму → «Создать» | новый документ в конце списка |
| форма с названием «ab» | ошибка валидации, код 400 |
| http://localhost:3000/item/99 или /abc | страница 404 |
| http://localhost:3000/error | страница 500 + стек ошибки в консоли сервера |
| консоль сервера | строки логгера для каждого запроса |

## 10. Частые вопросы на защите

- **«Где у вас layout?»** — `partials/header.ejs` + `partials/footer.ejs`, подключаются в каждой странице через `include`. Отдельного `layout.ejs` с `<%- body %>` нет, потому что EJS это не умеет без пакета `express-ejs-layouts`; задание допускает partials.
- **«Почему у обработчика ошибок 4 параметра, если `next` почти не используется?»** — Express определяет error handler по `fn.length === 4`. Плюс `next(err)` нужен, если заголовки уже отправлены.
- **«Почему `show` вызывает `next()` для несуществующего документа?»** — чтобы не дублировать логику 404: запрос сам дойдёт до общего `notFound`.
- **«Что будет после перезапуска?»** — добавленные документы пропадут, останутся 3 начальных: данные в памяти, без БД.
- **«Почему `<%=`, а не `<%-` для названия документа?»** — защита от XSS: пользователь мог ввести `<script>` в название.
